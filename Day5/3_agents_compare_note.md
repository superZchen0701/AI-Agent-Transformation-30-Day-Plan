# ReAct / Plan-and-Solve / Reflection 三范式对比笔记

> 同一任务，三种范式，实跑对照（DeepSeek-V4-Flash 模型）

## 一、统一对比任务

> 小明有 15 个苹果，给了小红 5 个，又从果园摘了 8 个，然后把剩余的苹果平均分给 3 个朋友，每个朋友得到几个？最后请把整个计算过程写成一首四句的中文小诗。

**为什么选这个任务**：含**多步算术**（15-5+8=18，18/3=6）+ **文本生成**（四句小诗）双段异质工作，对三种范式都是考验：

- ReAct：calculator 工具只能算数学，写诗必须 LLM 直接生成
- Plan-and-Solve：需规划多步 + 逐步执行
- Reflection：本次任务太简单，初版即最优，第 1 轮反思就判定"无需改进"——迭代价值未充分挖掘（更适合 Reflection 的应是含算法优化路径的任务，如素数题）

## 二、实跑结果对照

### 1. ReAct Agent

**关键日志**：

```
--- 第 1 步 ---
Thought: 需要先计算苹果数量，再写诗。用 calculator 计算 (15-5+8)/3。
Action: calculator[(15-5+8)/3]
Observation: (15-5+8)/3 = 6

# 注意：LLM 在第1步一次性输出了两个 Action 块（calculator + Finish[小诗]），
# _parseOutput 的 /Action:\s*(.*?)$/s 非贪婪到结尾，把整段（calculator + Finish）当成一个 Action
# _parseAction 的 ^(\w+)\[(.*)\]/s 贪婪匹配，toolName 误解析为 calculator，
# toolInput 含 ']' 导致 calculator 工具执行失败
Thought: 计算结果为6，每个朋友得到6个苹果。现在需要写一首四句中文小诗...
Action: Finish[小明十五苹果香，送人五个余十藏，果园又摘八个添，三友平分六个尝。]
❌ 执行工具 'calculator' 失败: Unexpected token ']'
Observation: 工具 'calculator' 执行失败: Unexpected token ']'

--- 第 2 步 ---
🎉 最终答案（LLM 直接输出，无 Action 包装）:
每个朋友得到 6 个苹果。
计算过程：15 - 5 + 8 = 18，18 ÷ 3 = 6。
小诗：
小明十五苹果香，
送人五个余十藏。
果园又摘八个添，
三友平分六个尝。
```

**结果**：**成功**（首次跑失败后修复 prompt + 加容错兜底，二次跑通）。

**真实跑通过程**（比预期更曲折）：

1. 第 1 步 LLM 一次性输出两个 Action 块（calculator + Finish\[小诗]），`_parseOutput` 解析时把整段当单个 Action，`_parseAction` 误把 `toolName` 解析为 `calculator`（贪婪正则匹配到第一个 `\w+`），导致 `calculator` 工具执行失败
2. 容错机制 1：`execute_tool` 内部 try/catch 把工具异常转为字符串 Observation 回传给 LLM（不中断循环）
3. 第 2 步 LLM 看到 calculator 失败的 Observation 后重新输出，这次直接给完整答案文本（无 `Action:` 前缀）→ `_parseOutput` 返回 `action=null`
4. 容错机制 2：`run()` 解析不到 Action 时兜底把 `content` 当最终答案返回

**修复要点**：

- 原 prompt 强制每步必带 `Action:` 前缀 → LLM 在无工具可调的纯文本子任务上崩
- 修复 1：prompt 加规则 3「任务含纯文本生成子任务且无对应工具时，可直接输出文本作为最终答案」
- 修复 2：`run()` 在解析不到 Action 时容错兜底，把整段 `content` 当作最终答案返回（不抛错）
- **既有容错**：`execute_tool` 内部 try/catch 把工具异常转为字符串 Observation，避免工具失败直接崩整个 Agent

**性能**：2 步内成功，约 2 次 LLM 调用 + 1 次工具失败重试，\~5 秒完成（步数最少但中途有解析异常）。

### 2. Plan-and-Solve Agent

**关键日志**：

```
--- 开始处理问题 ---
--- 正在生成计划 ---
✅ 计划已生成：
\`\`\`javascript
["计算小明给小红后剩余的苹果数：15 - 5 = 10",
 "计算小明从果园摘完后剩余的苹果数：10 + 8 = 18",
 "计算每个朋友分到的苹果数：18 ÷ 3 = 6",
 "将上述计算过程写成一首四句中文小诗"]
\`\`\`
--- 正在执行计划 ---
-> 步骤 1/4：15 - 5 = 10
-> 步骤 2/4：10 + 8 = 18
-> 步骤 3/4：18 ÷ 3 = 6
-> 步骤 4/4：写四句小诗

--- 最终结果 ---
十五减五剩十个，再加八来十八多；平均分给三朋友，每人六个乐呵呵。
```

**结果**：**成功**。4 步规划清晰、逐步执行、最终交付完整答案。

**亮点**：

- 规划阶段把复合任务**正确拆解**为 3 步算 + 1 步写诗
- 执行器每步用历史上下文保证步骤连贯
- 最终小诗虽"十八多"稍欠严谨（实际正好 18），但四句结构完整、押韵、含全部计算要素

**性能**：1 次规划 + 4 次执行 = 5 次 LLM 调用，约 15 秒完成。

### 3. Reflection Agent

**关键日志**：

```
--- 开始处理任务 ---
任务: 小明有 15 个苹果，给了小红 5 个，又从果园摘了 8 个，然后把剩余的苹果平均分给 3 个朋友，每个朋友得到几个？最后请把整个计算过程写成一首四句的中文小诗。

--- 正在进行初始尝试 ---
15减5剩10个，又摘8个成18，平均分给3朋友，每人正好6个果。
📝 记忆已更新，新增一条 'execution' 记录。

--- 第 1/3 轮迭代 ---

-> 正在进行反思...
当前产出计算正确、过程完整、四句成诗，满足任务要求；运算流程无冗余，资源占用可忽略。不存在根本上更优的方案，因此无需改进。
📝 记忆已更新，新增一条 'reflection' 记录。

✅ 反思认为产出已无需改进，任务完成。

--- 任务完成 ---
最终产出:
15减5剩10个，又摘8个成18，平均分给3朋友，每人正好6个果。
```

**结果**：**成功**。1 轮迭代就收敛（初始→反思1"无需改进"→停）——本次任务对 LLM 而言初版即最优，反思正确判断无需再优化。

**亮点**：

- Memory 模块完整记录"执行-反思"轨迹
- 第 1 轮反思就触发停止条件（正则匹配"无需改进"等变体），未过度迭代
- **流式输出**：`_sendMessages` 改为 `stream: true`，屏幕实时显示 LLM delta，避免长时间无输出不知道是否在跑
- 停止条件正则容错多种变体（`/无[需须]改进|不需[要]?改进|已(达到)?最优|已足够好/`）

**意外发现**：本次 Reflection 的 LLM 调用次数与 ReAct 并列最少（都是 2 次），与"成本最高"的预期相反。原因是任务太简单，LLM 一次就给最优解，反思也正确判定无需迭代。这反过来说明：**Reflection 的成本上限高，但实际成本随任务难度浮动**——简单任务上反而高效。

**性能**：1 次初始 + 1 次反思 = **2 次 LLM 调用**，约 5 秒完成（与 ReAct 并列最快）。

## 三、对比汇总表

| 维度           | ReAct                                | Plan-and-Solve                | Reflection                |
| ------------ | ------------------------------------ | ----------------------------- | ------------------------- |
| **任务结果**     | ✅ 成功（修复后）                            | ✅ 成功                          | ✅ 成功                      |
| **LLM 调用次数** | 2（最少，但含 1 次工具失败重试）                   | 5（1规划+4执行）                    | 2（1初+1反思，未触发优化）           |
| **完成耗时**     | \~5s                                 | \~15s                         | \~5s（并列最快）                |
| **核心机制**     | Thought→Action→Observation 循环 + 双层容错 | Planner 一次性规划 → Executor 逐步执行 | Execute→Reflect→Refine 迭代 |
| **结构强度**     | 强（prompt 强约束 + 工具异常容错 + 解析失败兜底）      | 中（规划器输出需解析 JSON）              | 弱（停止条件靠 LLM 输出文本匹配）       |
| **可解释性**     | 高（Thought 暴露推理过程）                    | 中（规划即说明书）                     | 中（轨迹可追溯）                  |
| **适用任务**     | 需动态调工具的探索性任务（含纯文本子任务也兼容）             | 目标明确、可预先拆解的复杂任务               | 高质量产出、需反复打磨的任务（本次未触发迭代）   |
| **鲁棒性**      | 中（依赖容错兜底，LLM 输出不规范时仍能跑通）             | 中（规划 JSON 解析失败会崩）             | 高（停止条件正则容错多种变体，未触发迭代反而最稳） |

## 四、适用场景总结

### 1. ReAct 适合：动态探索 + 工具密集型任务（容错后兼容纯文本子任务）

**典型场景**：

- 搜索引擎检索 + LLM 推理（如 Perplexity 类问答）
- 数据库查询 + 数据分析（Text-to-SQL + 结果解读）
- API 调用链（先调 A 拿到 id，再调 B 拿详情）
- 计算密集型推理（如多步数学题，每步必须用 calculator 验证）
- **混合任务**：工具调用 + 纯文本生成（如本次对比题——计算 + 写诗，加容错兜底后能跑通）

**优势**：

- Thought 透明可见，便于调试
- 工具调用准确（prompt 强制）
- 动态决策下一步（不预先规划全流程）
- LLM 调用次数最少（本次 2 次，步数最少）
- 双层容错（工具异常 + 解析失败）让 LLM 输出不规范也能跑通

**劣势**：

- 强约束格式，LLM 偶尔不遵从就崩（必须配容错兜底）
- 无容错时遇到纯文本子任务卡死
- `_parseOutput` 一次只能解析一个 Action 块，LLM 输出多个 Action 块时解析混乱（实跑踩坑）
- maxSteps 兜底是硬阈值，可能提前终止

### 2. Plan-and-Solve 适合：目标明确、可预拆解的复杂任务

**典型场景**：

- 多步数学题（如本次对比任务）
- 项目实施方案撰写（背景分析→方案设计→风险预案→执行计划）
- 复杂代码实现（架构设计→模块划分→编码→测试用例）
- 长文档撰写（大纲→各章节→润色）

**优势**：

- 规划先于执行，避免"走一步看一步"的局部最优
- 计划本身可审计（用户可看 LLM 怎么拆解的）
- 步骤间上下文累积，保证连贯

**劣势**：

- 规划一次定型，**无法应对中途发现的新信息**（动态性差）
- 规划质量决定全局成败（规划错了步步错）
- 依赖 LLM 输出可解析的结构化格式（如 JSON 数组）

### 3. Reflection 适合：高质量产出、需反复打磨的场景

**典型场景**：

- 代码生成（初版→反思算法效率→优化）
- 文案/营销稿撰写（初版→反思吸引力/准确性→优化）
- 学术写作（初稿→同行评审式反思→修订）
- 翻译（初译→反思信达雅→精修）

**优势**：

- 自我纠错机制，产出质量上限高
- 反馈可追溯（Memory 存所有迭代轨迹）
- 收敛条件灵活（"无需改进"等变体都能触发停止）
- **任务简单时自动止损**：初版即最优就不迭代，成本随任务难度浮动（本次只调 2 次就结束）

**劣势**：

- 反思质量依赖 LLM 自评能力（LLM 不知自己错在哪时就失效，可能误判"无需改进"放过问题）
- 成本上限高（max\_iterations 次反思+优化，复杂任务可能跑满）
- 对"明确最优解"的简单任务，反思价值低（本次即如此，第 1 轮就停）

## 五、选型决策树

```
任务需要外部工具调用吗？
├─ 是 → 任务能预先拆解为明确步骤吗？
│      ├─ 是 → 用 Plan-and-Solve（效率更高）
│      └─ 否 → 用 ReAct（动态决策）
└─ 否 → 任务对产出质量要求高吗？
       ├─ 是 → 用 Reflection（迭代优化）
       └─ 否 → 直接调 LLM 一次搞定，无需 Agent
```

## 六、混合范式展望

实际生产 Agent 通常是**三范式混合**：

- **Plan-and-Solve 做骨架**：先规划全局步骤
- **每步用 ReAct 执行**：动态调工具完成当前子任务
- **关键节点用 Reflection 把关**：对产出做反思+优化

代表实现：Manus / Claude Code / Cursor Composer 等生产级 Agent 都采用类似混合策略。Day5 后续可以尝试把三范式组合成一个 Meta Agent。

## 七、本对比的局限

1. **单任务单次跑**：未做多任务多次跑取平均，结果有随机性
2. **模型单一**：仅用 DeepSeek-V4-Flash，不同模型可能表现差异大
3. **任务偏简单导致 Reflection 价值未体现**：苹果+小诗任务对 LLM 太容易，初版即最优，第 1 轮反思就停止——LLM 调用次数反与 ReAct 并列最少（2 次）。更适合 Reflection 的应是素数题（初版试除法→反思→埃氏筛→欧拉筛）等含明确优化路径的任务，才能体现迭代价值
4. **ReAct 中途有 calculator 解析失败重试**：容错兜底解决了"无工具可调"的崩溃问题，但"步数最少"不代表"最稳健"
5. **流式输出差异**：reflection-agent.js 已改为流式输出（屏幕实时显示 delta），react-agent.js 和 plan-and-solve-agent.js 仍是非流式（屏幕长时间无输出）。生产环境应统一流式以提升用户体验

***

**结论**：三种范式各有适用域，无绝对优劣。理解每种范式的设计前提与失效边界，比追求"最强 Agent"更重要。生产级 Agent 通常是三范式混合：Plan-and-Solve 做骨架，ReAct 做单步执行，Reflection 做关键节点把关。
